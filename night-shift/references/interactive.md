# Night shift: starting, checking, stopping and changing a run

For an interactive session (the user's chat), not for a night session. Paths are relative to this skill's folder, the one that holds `SKILL.md` (a session finds it in `$NIGHT_SHIFT_SKILL`; the header names it too).

## When not to chain

A job of one piece (a fix, a review, a small feature) is done in the chat that asked for it. Each session of a chain starts fresh: it writes its fixed context again, about 38.4k tokens that every one of its calls then reads (the fixed part is about 15 % of a session's coordinator cost), and it ends with a night report and a handover that a chat does not need; `--goal` adds a planning session with its reviewer before the work begins. A chain pays off when the job has several pieces or has to go on while the user is away. When the user asks for a chain for a job of one piece, start it as asked, and say in the start message what the chain adds over the chat.

## Starting, checking, stopping

**Ask nothing once the user says to start a run**; the user wants no questions after saying so, since a question before the start left the chain waiting while the user thought it ran. An open choice, such as whether the chain may use the desktop or how far it goes, is decided from the recorded preferences (the project's last chain, its plan, memory), recorded with the work, started, and named in the start message. The user changes it afterwards through `inbox.md` or `stop`.

1. The tree must be committed (the runner refuses uncommitted work). On a machine or a repository that has not run a chain yet, run `node <skill folder>/scripts/night-chain.mjs doctor --repo <repo>` first: a `FAIL` line is something `start` would refuse or a guard that would not hold; fix what is yours to fix and tell the user what the rest needs.
2. Write the first continuation prompt to a file, in the shape `SKILL.md`'s last step gives `next-prompt.md`: one line that names the piece, then `## Rules`, `## State`, `## This piece` and `## Lessons for this piece`. In mode opus, a first piece that `references/mode-opus.md` allows may open with `MODEL: fable` (`MODEL: mythos` where the user's rules or words name Mythos). When the user gives a goal and no plan of pieces exists, write no prompt: pass the goal to `start` in the user's words, with `--goal <text>` or `--goal-file <file>` instead of `--prompt-file`. The runner wraps it in `references/goal.md`, whose first session writes the roadmap, has it reviewed, approves and commits it, and hands piece 1 on; the goal approves the work it needs and nothing beyond it.
3. Start the run with `node <skill folder>/scripts/night-chain.mjs start --repo <repo> --prompt-file <file>`. `start` takes `--mode opus|fable|mythos` (the model the run uses; each mode's rules for its sessions are in `references/mode-<mode>.md`, which the runner puts into every new session's header; a resumed one keeps the header it began with), `--lang <code>` (the language of the text the user reads: `en`, or a table of the user's own in `~/.claude/night-shift/lang/`) and `--attended` (config `"attended": true`; `--attended false` turns that off for one start) when the user says they are at hand but not watching, such as a job by day: no session waits for them, and each writes a question that needs them to `<state>/questions.md` at once and goes on (`references/attended.md`, which only such a run's sessions get). It prints one `rules:` line for each of the user's rule files in force, or `rules:  none`; tell the user which ones apply. It runs through Task Scheduler in a hidden console (`conhost --headless`), so closing the editor does not stop it and no window appears on the user's screen. The log is `<state>/chain.log` (or `status`), and `stop --now` is the emergency stop. `--window` gives it a visible console instead, whose closing stops the chain; use it only when the user asks to watch. A process without a console (a detached dev server) that starts a console program would open a Windows Terminal window, so every session's Node processes load `scripts/hide-windows.cjs` (through `NODE_OPTIONS`), which hides what they start. There is no end time: the chain goes on until a session writes `STOP` (no approved, unblocked work is left), two handovers fail in a row, or the user runs `stop`. A usage limit only pauses it: once the limit resets, the session it cut off goes on in the same conversation (`--resume`). If the chain was stopped in between, or ended because the reset was too far away (see below), `start` without a prompt resumes that session from the kept `<state>/resume.json`; `start` with a prompt starts fresh. The runner recognises the limit from the result's `api_error`/429 and the `rate_limit_event`, not the CLI's wording, which changes (tests: `node --test scripts/session-outcome.test.mjs`). `--until HH:MM` and `--max-sessions <n>` (the sessions this `start` runs) add a limit only when the user asks for one. **How a chain can end besides `STOP`, `--until` and `--max-sessions`** (the last line of `chain.log`, and what the user is told): `the usage limit resets <time>, more than <n> h away (--max-wait-hours)` or `…, after <HH:MM>` (the reset is farther than `--max-wait-hours`, default 6, or `"maxWaitHours"`, or past `--until`; `resume.json` or the handover stays for the next `start`); `session <nn> kept failing for <n> h (<error>)` (API or network errors, retried after 1, 2, 5, 10, 20 and then 30 minutes, the same conversation resumed when it had worked; they do not count toward the two failed handovers); `session <nn> cannot run: <error>` (a refused login or a bad request: tell the user to log in again, then `start` without a prompt); `the runner crashed: <error>`; `the seven-day window is at <n>%, at or over the <n>% weekly ceiling (--weekly-ceiling)` (`"weeklyCeiling"`), `this start's sessions cost $<n>, at or over the $<n> cap (--max-usd)` (`"maxUsd"`), and `the five-hour window is at <n>%, at or over 90%, and resets <time>, after <HH:MM>` or `…, more than <n> h away (--max-wait-hours)` (no session starts at or over 90 % of that window, and its reset is past `--until` or too far); each of these three keeps `next-prompt.md`, so a `start --state <that folder>` goes on once the window resets, or under a higher cap. To go on in an earlier run's folder (after `stop`, or on a new day, since the folder is named by date), add `--state <dir>`: it continues from that folder's `next-prompt.md` and session count.
   - **After a power cut, crash or restart** the chain stays down (its task has no trigger), and `status` says "not running" with no "chain ends" line. Run `start --repo <repo> --state <dir>` without a prompt. A session that `chain.log` shows as started and never ended goes on in its own conversation (`--resume`), with a note that its subagents died. Its uncommitted work is let through without `--allow-dirty`. If that resume fails, the usual retry starts a fresh session with a recovery note; a retried prompt keeps its `MODEL` and `EFFORT` lines on top, since the retry does the same piece.
   - **Model and effort:** the runner picks them, whatever the user runs meanwhile in VS Code or Desktop (Fable, another level). In mode opus a session runs on Opus (`--model opus`) at `xhigh`, unless its prompt opens with `MODEL: fable`, which `references/mode-opus.md` allows for one hard piece only: that session runs on Fable at `high`, and its header tells it to do only that piece. Fable's weekly allowance is the user's daytime work, so the runner gives a night session Fable only while less than 60 % of it is used (`--fable-ceiling`, `"fableCeiling"`), and while that share is unknown to at most two sessions in a chain (`--fable-sessions`, `"fableSessions"`). A `MODEL: fable` prompt it refuses, and a Fable session the allowance cuts off, run on Opus at `max`; `chain.log` and the report say why. Mythos is the same model under another name, open only to some accounts, on the same weekly allowance: `MODEL: mythos` has the same gate, the same count (the two count together), the same level and the same fall to Opus at `max`. A session on a model the account cannot run (refused as not found before any turn) does not end the chain: its piece runs on Opus at `max`, and so does every later ask for that model in the chain. A prompt that opens with `EFFORT: high`, `xhigh` or `max` runs that one session at that level; `max` is for when the user asks for it. The runner's own settings layer puts every Opus key at `xhigh`, every Fable and Mythos key at `high`, every Sonnet key at `medium`, every Haiku key at `high`, and `CLAUDE_CODE_SUBAGENT_MODEL` at `sonnet`. That layer wins over the user's and the project's files, while an environment variable loses to the project's settings (`scripts/effort.mjs`). In mode fable every session runs on Fable at `high`, in mode mythos on Mythos at `high`, and the runner never chooses `max` in either; a header says why a session runs on Opus instead, and a main model the account cannot run ends the chain (`session <nn> cannot run: …`), since only the user can change the mode. Change the chain's own model or level with `--model` and `--effort`, or `"model"` and `"effort"` in `.claude/night-shift.json` (an unknown key in that file stops `start`); `--model fable` alone means mode fable and `--model mythos` alone mode mythos. A night run loads no MCP server and the guard refuses MCP tools, unless the file's `"mcp"` lists the server (or is `"inherit"`). Never add `claude --effort` yourself: it lifts every subagent to that level. The same layer sets the output style to `default`: a headless session's prose has no reader, and the user's Explanatory style only added insight blocks.
4. Once `start` has returned (before, `wait` would find the last run's finished pointer), start the waiter: one Bash call with `run_in_background: true` running `node <skill folder>/scripts/night-chain.mjs wait --repo <repo>` (also when the user asks later to be told about a chain already running). It sleeps until the runner's process exits (a kernel wait, no polling), follows a `reload` to the next runner, and goes on through a usage-limit wait, which passes inside the runner. It then prints `status`'s first lines and what waits for the user. The waiter only reports: the chain does not depend on it, so it is not something "the chain needs" (below). If VS Code or this chat closes, only the waiter dies; the chain goes on, and the Telegram card still comes. It replaces any `status` loop or `sleep` of your own.
   - **In an attended run** (`--attended`) the waiter also wakes on each new question the sessions write to `<state>/questions.md`, with exit 3, while the chain goes on. Tell the user the question at once, with the session's pick and what changes if they pick otherwise, and start the waiter again the same way (it keeps what it reported in `<state>/wait.json`, so it reports only what is new; one waiter per state folder). When the user answers, append a line `A<n>: <answer>` to `<state>/inbox.md`; the next session applies it before anything else. From the phone, `/inbox A<n>: <answer>` in the bot's chat does the same once `telegramInbox` is on. A hard stop asked so (a push, a merge) is the user's to do by hand. Write nothing else into the state folder. Each wake is one turn of this chat. **A user without Telegram** can answer from the phone through this chat: Remote Control (`/remote-control` or `/rc` in it, "Control this session from your phone or claude.ai/code"; a claude.ai login, Pro plan or higher) shows this chat in the Claude app and on claude.ai/code. Say so in an attended run's start message when `~/.claude/night-shift/telegram.json` does not exist.
   - **When it wakes you,** read its output (for more, `status` or the night report) and answer in the user's language and tell the user how the chain ended, its problems, and the list of what waits for the user. In the language the run is set to, `wait` labels that list `Waiting for the user`. Start nothing yourself, the list's items included: no push, no new round, no restart. Exit 0: the chain ended. Exit 2: its runner died without an end line (`the chain crashed`, in the language the run is set to); say so and give the user the `start … --state` command it printed.
5. Tell the user five things: the state folder, that it runs until the work is done, `status` / `stop [--now]`, where the report is, and that this chat says when the chain ends while it stays open (Telegram either way).

## Reports and Telegram

Reports cost no tokens. `status` prints the full one: problems, jobs, tokens per model for the main agent, subagents and workflow agents, the limit timeline, and commits. When `~/.claude/night-shift/telegram.json` holds `{ "token": … }`, the runner also starts `scripts/night-report.mjs watch`. It sends Telegram a short card (`scripts/telegram-cards.mjs`) when a session ends: its title and next step from the night report, the numbers, how far the chain is with an estimated end, its own problems, and its new waits in one collapsed quote. The user wants every message short: no commit hashes, token rows or prompt boilerplate, which stay in `status`. It sends one line when the chain waits for a limit, resumes or retries (the first two silently), a session of an attended run writes a question to `<state>/questions.md` (with a sound), a session is quiet for 30 minutes, or a session's first calls ran at another effort than the one the runner started it at (read from its transcript), and a summary card when the chain ends or its runner dies. A job's card lists a wrong effort as a problem. In the bot's chat, `/status` answers with what runs now, including its effort and the progress, and `/report` with this run's jobs one line each, the progress, problems and what waits. `/stop` stops the chain after the session in progress and `/stop now` at once, as `stop [--now]` does (`scripts/runs.mjs`, `stopRun`); the bot answers before the kill, and after `/stop now` no end card follows. `/inbox <text>` adds the text to `<state>/inbox.md` after the time; it is off until the user's global `config.json` holds `"telegramInbox": true` (only that file may hold the key). The progress counts this run's jobs that ended well against the last section's `**Remaining:**` count (only the jobs done until a section has one); the estimate adds the jobs left at this run's mean working time, from the end of a limit wait if one runs. Every Telegram request has its own timeout and a failed poll is retried after 3 s; the watcher writes each command's delay and every Telegram error to `<state>/watch.log`. Preview a card with `night-report.mjs card --state <dir> [--nn <n> | --chain]`. A session's night-report section should keep its `**Waits for you**` split into `- New:` and `- Still waiting …:`, since the card lists only the new ones. To set it up: create a bot with BotFather, save the token, have the user press Start, then run `node scripts/night-report.mjs telegram-setup`.

## While a run is active

An interactive session does not edit the tree. Both would be writing to the same branch. Check with `status` first.

**Changing a running chain.** Nothing the chain needs may live in an interactive session. Closing VS Code or a terminal must change nothing; only `stop` stops the chain. So never `stop` it and leave a waiter in your session to restart it: when the editor closes, the waiter dies and the chain just ends. (The `wait` of step 4 restarts nothing; it only reports.)
- **Settings:** every new session reads `<state>/night-settings.json`, so an added `env`, `modelSettings` or hook there applies from the next session on. `start` keeps what was added and rewrites only the guard, the limit wait, the subagent model, the efforts and `crossSessionInbound`, which is always `refuse`, so the sessions take no message from the user's other sessions (it also sets the output style to `default` when none was added). A change every run needs belongs in `runChain`.
- **Work or rules for the sessions:** write them into `<state>/inbox.md` (work the user approved after the start, a rule that changed). The next session reads it first; at its end it moves the file into `prompts/`, reads the moved file and carries what is not done into its continuation prompt (`SKILL.md`, "Inside a night session"). Never edit `next-prompt.md` while a session runs: that session writes over it when it ends.
- **Runner or report code:** run `night-chain.mjs reload --repo <repo>`. After the session in progress (and a limit wait, if one runs), a fresh runner with the code now on disk takes over through the scheduled task, in a hidden console, and so does a new watcher. A runner started in a visible console (by hand, or by a runner from before 2026-11-05) moves itself to a hidden one the same way. A runner from before `reload` says so and ignores the request; give it settings changes instead. Tests: `node --test scripts/*.test.mjs`.
- **The skill itself** (`SKILL.md`, this file, `scripts/wait-for.mjs`): every new session reads the copy on disk, so a change applies from the next session on without `reload`.
