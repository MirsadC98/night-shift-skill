# Night shift: starting, checking, stopping and changing a run

For an interactive session (the user's chat), not for a night session. Paths are relative to the skill's folder, `~/.claude/skills/night-shift/`.

## Starting, checking, stopping

**Ask nothing once the user says to start a run** (the user's rule: "gece vardiyasını çalıştır dedikten sonra bir daha böyle sorular sorma"; a question before the start left the chain waiting while the user thought it ran). An open choice, such as whether the chain may use the desktop or how far it goes, is decided from the recorded preferences (the project's last chain, its plan, memory), recorded with the work, started, and named in the start message. The user changes it afterwards through `inbox.md` or `stop`.

1. The tree must be committed (the runner refuses uncommitted work).
2. Write the first continuation prompt to a file, in the shape `SKILL.md`'s last step gives `next-prompt.md`: one line that names the piece, then `## Rules`, `## State`, `## This piece` and `## Lessons for this piece`. A first piece that `SKILL.md`'s "Model and effort" allows may open with `MODEL: fable`.
3. Start the run with `node ~/.claude/skills/night-shift/scripts/night-chain.mjs start --repo <repo> --prompt-file <file>`. It runs through Task Scheduler in a hidden console (`conhost --headless`), so closing the editor does not stop it and no window appears on the user's screen. The log is `<state>/chain.log` (or `status`), and `stop --now` is the emergency stop. `--window` gives it a visible console instead, whose closing stops the chain; use it only when the user asks to watch. A process without a console (a detached dev server) that starts a console program would open a Windows Terminal window, so every session's Node processes load `scripts/hide-windows.cjs` (through `NODE_OPTIONS`), which hides what they start. There is no end time: the chain goes on until a session writes `STOP` (no approved, unblocked work is left), two handovers fail in a row, or the user runs `stop`. A usage limit only pauses it: once the limit resets, the session it cut off goes on in the same conversation (`--resume`). If the chain was stopped in between, `start` without a prompt resumes that session; `start` with a prompt starts fresh. The runner recognises the limit from the result's `api_error`/429 and the `rate_limit_event`, not the CLI's wording, which changes (tests: `node --test scripts/session-outcome.test.mjs`). `--until HH:MM` and `--max-sessions <n>` add a limit only when the user asks for one. To go on in an earlier run's folder (after `stop`, or on a new day, since the folder is named by date), add `--state <dir>`: it continues from that folder's `next-prompt.md` and session count.
   - **After a power cut, crash or restart** the chain stays down (its task has no trigger), and `status` says "not running" with no "chain ends" line. Run `start --repo <repo> --state <dir>` without a prompt. A session that `chain.log` shows as started and never ended goes on in its own conversation (`--resume`), with a note that its subagents died. Its uncommitted work is let through without `--allow-dirty`. If that resume fails, the usual retry starts a fresh session with a recovery note; a retried prompt keeps its `MODEL` and `EFFORT` lines on top, since the retry does the same piece.
   - **Model and effort:** the runner picks them, whatever the user runs meanwhile in VS Code or Desktop (Fable, another level). A session runs on Opus (`--model opus`) at `xhigh`, unless its prompt opens with `MODEL: fable`, which `SKILL.md`'s "Model and effort" allows for one hard piece only: that session runs on Fable at `high`, and its header tells it to do only that piece. Fable's weekly allowance is the user's daytime work, so the runner gives a night session Fable only while less than 60 % of it is used (`--fable-ceiling`, `"fableCeiling"`), and while that share is unknown to at most two sessions in a chain (`--fable-sessions`, `"fableSessions"`). A `MODEL: fable` prompt it refuses, and a Fable session the allowance cuts off, run on Opus at `max`; `chain.log` and the report say why. A prompt that opens with `EFFORT: high`, `xhigh` or `max` runs that one session at that level; `max` is for when the user asks for it. The runner's own settings layer puts every Opus key at `xhigh`, every Fable key at `high`, every Sonnet key at `medium`, every Haiku key at `high`, and `CLAUDE_CODE_SUBAGENT_MODEL` at `sonnet`. That layer wins over the user's and the project's files, while an environment variable loses to the project's settings (`scripts/effort.mjs`). Change the chain's own model or level with `--model` and `--effort`, or `"model"` and `"effort"` in `.claude/night-shift.json`. Never add `claude --effort` yourself: it lifts every subagent to that level. The same layer sets the output style to `default`: a headless session's prose has no reader, and the user's Explanatory style only added insight blocks.
4. Once `start` has returned (before, `wait` would find the last run's finished pointer), start the waiter: one Bash call with `run_in_background: true` running `node ~/.claude/skills/night-shift/scripts/night-chain.mjs wait --repo <repo>` (also when the user asks later to be told about a chain already running). It sleeps until the runner's process exits (a kernel wait, no polling), follows a `reload` to the next runner, and goes on through a usage-limit wait, which passes inside the runner. It then prints `status`'s first lines and what waits for the user. The waiter only reports: the chain does not depend on it, so it is not something "the chain needs" (below). If VS Code or this chat closes, only the waiter dies; the chain goes on, and the Telegram card still comes. It replaces any `status` loop or `sleep` of your own.
   - **When it wakes you,** read its output (for more, `status` or the night report) and tell the user in Turkish how the chain ended, its problems, and the "Kullanıcıyı bekleyenler" list. Start nothing yourself, the list's items included: no push, no new round, no restart. Exit 0: the chain ended. Exit 2: its runner died without an end line ("zincir çöktü"); say so and give the user the `start … --state` command it printed.
5. Tell the user five things: the state folder, that it runs until the work is done, `status` / `stop [--now]`, where the report is, and that this chat says when the chain ends while it stays open (Telegram either way).

## Reports and Telegram

Reports cost no tokens. `status` prints the full one: problems, jobs, tokens per model for the main agent, subagents and workflow agents, the limit timeline, and commits. When `~/.claude/night-shift/telegram.json` holds `{ "token": … }`, the runner also starts `scripts/night-report.mjs watch`. It sends Telegram a short card (`scripts/telegram-cards.mjs`) when a session ends: its title and next step from the night report, the numbers, how far the chain is with an estimated end, its own problems, and its new waits in one collapsed quote. The user wants every message short: no commit hashes, token rows or prompt boilerplate, which stay in `status`. It sends one line when the chain waits for a limit, resumes or retries (the first two silently), a session is quiet for 30 minutes, or a session's first calls ran at another effort than the one the runner started it at (read from its transcript), and a summary card when the chain ends or its runner dies. A job's card lists a wrong effort as a problem. In the bot's chat, `/durum` answers with what runs now, including its effort and the progress, and `/rapor` with this run's jobs one line each, the progress, problems and what waits. The progress counts this run's jobs that ended well against the last section's `**Remaining:**` count (only the jobs done until a section has one); the estimate adds the jobs left at this run's mean working time, from the end of a limit wait if one runs. Every Telegram request has its own timeout and a failed poll is retried after 3 s; the watcher writes each command's delay and every Telegram error to `<state>/watch.log`. Preview a card with `night-report.mjs card --state <dir> [--nn <n> | --chain]`. A session's night-report section should keep its `**Waits for you**` split into `- New:` and `- Still waiting …:`, since the card lists only the new ones. To set it up: create a bot with BotFather, save the token, have the user press Start, then run `node scripts/night-report.mjs telegram-setup`.

## While a run is active

An interactive session does not edit the tree. Both would be writing to the same branch. Check with `status` first.

**Changing a running chain.** Nothing the chain needs may live in an interactive session. Closing VS Code or a terminal must change nothing; only `stop` stops the chain. So never `stop` it and leave a waiter in your session to restart it: when the editor closes, the waiter dies and the chain just ends. (The `wait` of step 4 restarts nothing; it only reports.)
- **Settings:** every new session reads `<state>/night-settings.json`, so an added `env`, `modelSettings` or hook there applies from the next session on. `start` keeps what was added and rewrites only the guard, the limit wait, the subagent model and the efforts (it also sets the output style to `default` when none was added). A change every run needs belongs in `runChain`.
- **Work or rules for the sessions:** write them into `<state>/inbox.md` (work the user approved after the start, a rule that changed). The next session reads it first and moves it into `prompts/` once its items are done or carried into the continuation prompt (`SKILL.md`, "Inside a night session"). Never edit `next-prompt.md` while a session runs: that session writes over it when it ends.
- **Runner or report code:** run `night-chain.mjs reload --repo <repo>`. After the session in progress (and a limit wait, if one runs), a fresh runner with the code now on disk takes over through the scheduled task, in a hidden console, and so does a new watcher. A runner started in a visible console (by hand, or by a runner from before 2026-11-05) moves itself to a hidden one the same way. A runner from before `reload` says so and ignores the request; give it settings changes instead. Tests: `node --test scripts/*.test.mjs`.
- **The skill itself** (`SKILL.md`, this file, `scripts/wait-for.mjs`): every new session reads the copy on disk, so a change applies from the next session on without `reload`.
